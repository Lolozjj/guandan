# 掼蛋牌面识别（YOLO）

> **接手这个项目请先读 [`HANDOFF.md`](HANDOFF.md)** —— 里面有当前状态、下一步、
> 实测参数和踩过的坑。这份 README 偏"是什么/怎么做"，HANDOFF 偏"现在到哪了/接着做什么"。

用 YOLO 识别微信小程序掼蛋的牌面。检测目标是**每张牌左上角的角标**（点数 + 花色），54 类。

数据问题已通过「**提取游戏原生素材 + 程序合成 + 自动标注**」解决，全程无需人工标注。


---

## 快速上手：怎么看效果

三条命令，从"看单张图"到"看整体指标"：

```powershell
# 1. 单张截图 -> 牌列表（文字输出，最直观）
.venv/Scripts/python.exe predict_cards.py runs/detect/guandan4/weights/best.pt shots/img.png --imgsz 960 --level 2

# 2. 生成效果图：截图 + 检测框（按花色配色）+ 下方识别结果面板
.venv/Scripts/python.exe make_result.py runs/detect/guandan4/weights/best.pt shots/img_5.png

# 3. 在带人工真值的真实截图上评估 —— 唯一可信的指标
.venv/Scripts/python.exe eval_real.py runs/detect/guandan4/weights/best.pt --imgsz 960
```

| 参数 | 说明 |
|---|---|
| `--imgsz` | 推理分辨率，训练用的是 960，推理保持一致 |
| `--level` | 当前级牌点数（掼蛋打几），只影响排序显示 |
| `--conf` | 置信度阈值，默认 0.25 |

产物位置：效果图在 `results/`，评估的标注图在 `runs/real_eval/`。

**⚠️ 两个脚本都会强制覆盖 `model.model.names`。** 权重文件内置了训练时的类别名，
如果那份 `data.yaml` 的顺序和 `synth/layout.py` 的 `CLASSES` 不一致，读出来的名字会整体错位
——**模型本身没学错，只是被念错了**。历史上真发生过一次，见「踩过的坑」第 3 条。

## 合成数据管线

```powershell
# 1. 从游戏本地缓存提取牌面素材（一次性；缓存位置见 assets/EXTRACTED.md）
python extract_unity_assets.py "<bundle目录>" assets/cards --filter commoncard

# 2. 抠出干净牌面底色（一次性）
python synth/make_card_bg.py

# 3. 抠出干净桌面背景（截图更新后需重跑）
python synth/make_bg.py

# 4. 批量生成数据集
python synth/generate.py --n 3000 --out dataset --seed 20260923

# 只看效果，不写数据集
python synth/generate.py --n 8 --preview
```

### 精度

合成的牌面与游戏真实渲染**平均绝对差约 2/255**，即只剩抗锯齿噪声。
牌面图案是游戏原生的、布局按实测参数生成，因此不存在「合成图与真实图分布不一致」的问题
—— 这正是公开的 Roboflow 类模型失败的原因。

## 实测参数

### 布局

| 参数 | 值 |
|---|---|
| 截图尺寸 | 1670×990 ~ 1688×999 |
| 卡片尺寸 | 132×174 px（圆角半径 8px） |
| 水平步长 | **95 px**（6 张截图上完全一致） |
| 竖向级联 | **62 px**（同点数的牌竖向错开，让每张都露出左上角） |
| 底部对齐 | 最底下那张牌顶边 y = 714，卡底 888 |
| 水平居中 | 整手牌在画面里居中 |
| 角标标注框 | 相对卡片左上角 (8, 1)，尺寸 93×66 |
| 出牌区 | 牌缩放 0.78（105×139），水平步长 100 |

**结构规则**：手牌按掼蛋牌序降序排列（大王 > 小王 > 级牌 > A > K > … > 3），
同点数的牌占一「列」，列内从顶部依次下移 62px，最后一张落在 y=714。

### 牌面拼装

```
牌面 = 白底圆角卡 + 点数图形(9,5,×1.02) + 小花色(58,17,×1.12) + 大花色pip(58,94,×2.24)
点数颜色随花色： ♠♣ 用黑， ♥♦ 用红
```

**级牌红桃（逢人配）是例外**：它的**小花色符号是金色**（用 `huase_5`），但大花色 pip 仍是红色。
实测：真实级牌 ♥5 的小符号 BGR (76,118,196)，合成 level 匹配时 (78,119,200)，不匹配时 (23,29,176) 纯红。

所以合成时每个类别要按 **13 种级牌各渲染一份** —— 这是同一类别内部的合法外观差异，
模型必须都见过，否则遇到金色 ♥ 会掉置信度（实测掉到 0.49）。

游戏不存 54 张整图，而是用零件运行时拼装。提取到的 sprite：

| Sprite | 内容 |
|---|---|
| `LargeCard_commom_shuzi_{hei,hong}_{1..13}` | 点数，1=A, 11=J, 12=Q, 13=K |
| `LargeCard_huase_{1..4}` | ♠ ♥ ♣ ♦（huase_5 是金色♥，级牌高亮用） |
| `LargeCard_king_14` / `_15` | JOKER 小王 / 大王 |

完整映射见 [`assets/EXTRACTED.md`](assets/EXTRACTED.md)。

## 踩过的坑

数据合成这条路真正的风险不是「造不出来」，而是**造出来的东西和真实有多像 —— 这件事只能靠真实数据验证，
不能靠合成 val 的分数**。下面每个坑都是这个教训的实例。

| # | 坑 | 症状 | 性质 |
|---|---|---|---|
| 1 | `fliplr=0.5`（ultralytics 默认） | 牌面镜像成无效字符，一半样本标签错误 | **真错误**。通用 CV 默认值套到有语义方向的任务上 |
| 2 | `layout.SUITS = "SHDC"` | 同点数分组内黑红牌位置对调，相邻角标框内像素颜色整个反过来 | **真错误**。实测真实顺序是 `S` `C` `D` `H`（先黑后红） |
| 3 | `data.yaml` 类别顺序与 `CLASSES` 不一致 | 26 张牌**全部恰好 rank+1**、花色全对，唯一例外是唯一不受影响的类别(王) | **假错误**。模型学对了，是 `names` 表念错了。现已改为脚本从 `CLASSES` 生成，不手写 |
| 4 | 布局居中公式差 2px + 无任何光度增强 | 模型对像素级差异零容忍（位置偏 1px，角标区差异就从 4.66 涨到 9.77/255） | 鲁棒性缺陷。改为加位置抖动 + 亚像素平移 + 模糊/亮度/噪点 |
| 5 | 大小王当成两列、顺序相反 | 同时持有大小王时列结构出错 | **真错误**。实测两张王共占一列，小王在上、大王在下 |
| 6 | 王牌拼装 | 角标区差异 48/255（普通牌约 3） | **已知不足**，见下面的「王牌的固有歧义」 |

### 王牌的固有歧义（不是 bug，是游戏布局本身的限制）

实测：把 img_3 两张王**同一相对位置**的区域对齐相减，平均差只有 **3.2/255**——就是噪声水平，**完全一样**。

原因：一手牌里同时有大小王时，上面的那张被下面那张盖住，**露出来的只有竖排 "JOKER" 文字，
而两张王的文字完全相同**（都是红色，都用 `king_15` 那个 sprite）。真正区分它们的小丑图案，
在被遮挡的那张上根本看不见。

所以「一张被遮挡的王无法辨认」是**游戏布局的固有限制**，不是模型能力问题——
人被问到同样的问题也答不出来。当前的做法是：上面那张按「高级牌在上」的惯例标注
（这是个推断，不是观察），模型答错了也不算它的问题。

**要绕开的话**，可以在后处理里加一条领域规则：同组两张王时，可见的那张认出来后，
另一张按固定顺序推出。但这需要先确认游戏确实总是按固定顺序显示大小王（目前只有一个样本）。

### 评估脚本自身的坑（也会骗人）

指标不只会被数据坑，也会被**评估代码**坑。这两个都实际发生过：

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 7 | 真值用「列号 + 布局模型」推导位置 | img_5 的列 7/8/9 各塞了两个不同点数的分组，不符合模型，位置全错 | 真值改用**绝对坐标**，测试集不依赖布局假设 |
| 8 | 贪心匹配「每个真值找最近检出」 | 同一张牌常有高低两个框（H6@0.77 与 D9@0.31 只差 **0.4px**），最近的不一定对，把正确的挤成误检 | 改为**按置信度从高到低**处理检出，让正确的框优先认领 |
| 9 | 真值只标手牌，桌面出牌区没标 | 模型正确检出桌面上的牌，被算成误检（img_5 有 4 个 conf 0.7~0.94 的"误检"其实是桌面牌） | 按框中心 y 区分，桌面检出单独统计 |

第 8、9 条合起来曾把真实准确率从 **99.2% 压到 91.4%**——**评估代码的 bug 让结论看起来比实际差得多**，
差点导致我去"优化"一个本来没问题的模型。

### 靠用户反馈发现的

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 11 | **级牌红桃的小花色符号是金色**，合成数据里一直是红色 | 实战识别 img_7 的级牌 ♥5 时置信度只有 **0.49**（形状一样所以猜对了，但没把握） | 合成器接受 `level` 参数，级牌 ♥ 的小符号改用 `huase_5`（金色 sprite）；生成时每个类别按 13 种级牌各渲染一份 |
| 12 | 核验脚本把**花色图案的边**当成了卡片左边 | 报"模型漏检"，实际是图案边缘落在栅格线附近 | 加判据：卡片左边缘贯穿整条可见带（62px），图案的边只有几十像素 |
| 13 | 卡片层级实际有 **7 层**（342/404/466/528/590/652/714） | 核验脚本只列了 6 层（403 起），img_6 最上面那张 7 在 y=342 检查不到 | 层级表补全 |

第 11 条的价值在于：**它是我完全没意识到的一个类别内变体**。素材提取时就发现 `huase_5` 是金色♥，
我还把它写进了文档，但合成时一次都没用上——文档记了、代码没用，等于没记。

### 最值得记的一条：报警信号被我解释掉了

| # | 坑 | 症状 | 修法 |
|---|---|---|---|
| 10 | 手牌卡片层级有 **6 层**（403/465/527/589/651/713），我的检测从 `y=498` 开始扫 | 每个列少算最上面 1~2 张，img_5 的真值少了 4 张牌（4♦ 4♥ 10♣ 9♠） | 扫描起点改到 403 以上 |
| 10b | `HAND_TOP = 515` 用手牌/桌面的 y 阈值划分 | 手牌最上面两层被当成桌面牌，`predict_cards` 少读 4 张 | 改用**按列底部对齐**判据（手牌每列都对齐最底行，桌面出牌区是浮动的） |

**这一条是用户发现的，不是我自己发现的**，而当时其实有信号：

img_5 的真值在自校验时报过警——「每列牌数应该等于该列点数」这条规则在列 7/8/9 上不成立
（3♦ 里混着 2♣2♥、10♦ 里混着 7♠7♥）。我当时的处理是**把它归因成"布局模型不适用"**，
而不是去查我的列检测是不是错了。**那个报警是对的，我解释错了。**

正确的反应是：自校验规则失败时，先假设自己的检测有问题，而不是先假设规则不适用。

第 3 条最值得记：**它的症状太整齐了**——所有牌恰好错一位、花色全对、唯一的例外正好是唯一不受影响的类别。
整齐到这个程度反而不可能是模型学错。如果只盯着「准确率 3.7%」这个数字，很容易误判成「合成数据这条路不行」而放弃。

## 真实测试集

`eval_real.py` 里的人工标注真值，读法是：把每列的角标裁出来看，再用「**每列牌数必须等于该列点数**」自校验。

| 截图 | 牌数 | 状态 |
|---|---|---|
| `img.png` | 27 | ✅ 已标 |
| `img_1.png` / `img_2.png` | 26 | ✅ 已标（img.png 的后续时刻，J♥ 已打出，列数 12→11） |
| `img_3.png` | 26 | ✅ 已标 |
| `img_4.png` | 5 | ❌ 未纳入：手牌太小 |
| `img_5.png` | 23 | ❌ 未纳入：列结构自校验不过，左边界疑似少识别一列 |

后两张需要单独处理左边界识别，才能纳入。

### 真值必须独立核验

**标真值这件事我错了两次**（img_5 少 4 张、img_3 少 1 张），都是用户发现的。
原因都是同一个：列检测的扫描起点写死在 `y=498`，把手牌最上面 1~2 层（403、465）切掉了。

所以 `verify_gt.py` 用**完全独立的方法**复查：

- 手牌的左边缘精确落在 `x0 + 95k` 上，在图像里是一条强竖直边缘
- 实测「有牌的层」梯度 190~300，「没牌的层」0~55，阈值 120 分得很干净
- 手牌分组是**从最底层连续往上**摞的，中断处以上不算（排除按钮、出牌区的干扰）

```powershell
.venv/Scripts/python.exe verify_gt.py
```

5 张截图目前全部通过。**加新截图后务必跑一次**——真值错了会让指标看起来像模型的问题。

## 路线图

### 阶段 0 — 环境 ✅

见上。

### 阶段 1 — 现成权重零样本摸底 ✅ 结论：不可用

从 Hugging Face 下载了 2 个扑克牌检测模型（52 类、角标标注、合成数据训练），
在真实照片上**全部零检出**——conf 一路降到 0.01 仍是 0 个框；但在它们自己的训练数据上工作正常。
说明是**域差异致命**，不是权重损坏。完整分析见 [`models/FINDINGS.md`](models/FINDINGS.md)。

结论：
1. ✅ **角标检测方案得到第三方印证**——公开数据集标注的也是角标，不是整张牌
2. ❌ 掼蛋自有数据是必需项，不是"效果不好再补"的优化项
3. ❌ 不要从这些权重微调起步（牌面图案不匹配），应从 `yolo11n.pt` 起步

### 阶段 2 — 数据 ✅ 已由「素材提取 + 合成」取代

原计划手工截图 + 手工标注，现已改为从游戏缓存提取原生素材、程序合成训练数据。
详见上面的「合成数据管线」。

**一个纠正**：早期版本的本 README 说"掼蛋四家手牌朝向不同、训练必须开 `degrees`"——**这是错的**。
实测（截图验证）所有牌都是正向的，包括四家的出牌区。`degrees` 不是必需项。

### 阶段 3 — 标注 ✅ 已由自动标注取代

合成数据的标注由坐标算出，无需人工。原手工标注方案（X-AnyLabeling）已不需要。

### 阶段 4 — 训练 ✅

```powershell
  project=C:/Users/17837/PycharmProjects/yolo/runs/detect name=guandan exist_ok=True
```

⚠️ **`fliplr=0.0` 不能省**（默认是 0.5）。牌面左右镜像后是**无效的牌**（"3" 镜像成 "Ɛ"），
但标注仍是同一个类 —— 等于给一半样本喂错误标签，直接破坏点数区分能力。同理 `flipud`、`degrees` 也要关。
通用 CV 的默认增强对「牌面」这种有语义方向的目标不适用。

⚠️ `project` 参数是相对 `runs_dir` 解析的，写 `project=runs/detect` 会得到 `runs/detect/runs/detect/`。
要固定输出位置就写绝对路径。

### 阶段 5 — 评估 ✅（用真实截图，不要看 val）

合成数据的 val 集来自训练同一个分布，分数必然虚高——**实测过：合成 val mAP50 0.993，
同期的真实截图准确率只有 3.7%**（当时有配置 bug）。所以 val 分数只能说明「训练有没有跑起来」。

唯一可信的指标是 `eval_real.py`：

```powershell
python eval_real.py runs/detect/guandanXX/weights/best.pt --imgsz 960
```

它在一批**人工逐张核对过真值**的真实截图上跑，输出检出率、端到端准确率、误检数和分错明细。

⚠️ 脚本里会强制覆盖 `model.model.names`。权重文件内置了训练时的类别名，若那份 `data.yaml`
的顺序和 `synth/layout.py` 的 `CLASSES` 不一致，读出来的名字会整体错位——模型本身没学错，只是被念错了。

### 阶段 6 — 集成 ✅（离线部分）

```powershell
python predict_cards.py runs/detect/guandanXX/weights/best.pt shots/img.png --imgsz 960 --level 2
```

输出按掼蛋牌序排好的手牌列表，并按点数分组便于核对。

后处理做了两件必要的事：
- **同位置去重** —— 同一张牌常出高低两个框（类别还可能不同），保留置信度最高的
- **区分手牌 / 桌面出牌区** —— 按框中心 y 划分

排序键实现了掼蛋牌序：`大王 > 小王 > 级牌 > A > K > ... > 3`，级牌用 `--level` 指定。

**还没做**：实时运行的图像来源（截屏流 / 录屏 / 小程序模拟器），三条路差别很大，需要单独设计。

### 阶段 7 — 调优（按需）

当前 128 张真值只错 1 张，且那 1 张是游戏布局的固有限制。暂时没有需要调的地方。
若之后扩充真实截图后发现新问题，按下面的表处理。

| 症状 | 处理 |
|---|---|
| 真实截图漏检 | 补真实截图做微调；加大合成数据的随机性 |
| 小目标漏检 | 换 `yolo11n-p2.yaml`，加 P2 小目标检测头 |
| 花色混淆严重 | 降级两级方案（见下）或提高 `imgsz` |
| 重叠严重时漏检 | 提高 `imgsz`，或调 NMS 的 `iou` 阈值 |

## 备选方案：两级检测

如果直接 54 类角标检测效果不达标，退到两级：

1. YOLO 只检测「牌的可见区域」——**1 类**，标注成本极低，抗遮挡
2. 从每个框里裁出左上角小图，缩放到统一尺寸
3. 小分类网络（或模板匹配）识别点数 + 花色

劣势：两段式，误差累积，工程复杂度更高。**先试方案一，不行再退。**
