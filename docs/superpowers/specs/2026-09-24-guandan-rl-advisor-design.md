## 1. 目标与成功判据

### 目标

PC 微信掼蛋旁边挂一个面板，**轮到我时给出出牌建议**。

**明确排除**：替用户出牌、往游戏发任何报文。模型只输出给人看的建议。

### 成功判据（按顺序）

1. **模拟器正确** —— 55 局真实记录里，每一手的真实着法都能被枚举出来（见 §6）
2. **模型打得过贪心基线** —— 不是"胜率有涨"，是明确打过"有牌就出最小"的基线
3. **影子模式在真机上没大问题** —— 模型建议与人类实际选择的分歧，可解释

三条都达成才算成功。第 2 条是分水岭：打不过贪心说明 RL 没跑起来，该查代码而不是加大训练量。

### 已知的时间尺度

**周到月级**（用户知情）。训练期间面板上没有推荐可看，因为**不写规则版垫底**（用户明确决定）。

## 2. 已确认的事实（都带证据，别重新推导）

### 2.1 炸弹顺序

```
4炸 < 5炸 < 同花顺 < 6炸 < 7炸 < 8炸 < 天王炸(四大天王)
```

**用户口述给出**，非规则书抄录。数据交叉验证：同一轮内的「被压 → 压」证据 24 对，
**0 条矛盾**（判据：**同一座位再次出牌 = 新的一轮**，否则就是压牌）。

```
4炸 → 4炸 ×11   4炸 → 5炸 ×4   5炸 → 7炸 ×4
4炸 → 7炸 ×2    5炸 → 5炸 ×1   7炸 → 7炸 ×1   5炸 → 6炸 ×1
```

同档内（4炸→4炸）比主点数，数据自证。

⚠️ **「同花顺夹在 5炸和 6炸之间」这半边数据未覆盖**，仅凭用户口述。
实施时在规则表里标注来源，遇到反例从这里查。

### 2.2 游戏牌型表（从协议 `card_type` 字段统计，465 手真牌）

| card_type | 张数 | 牌型 |
|---|---|---|
| 1 / 2 / 3 | 1 / 2 / 3 | 单张 / 对子 / 三张 |
| 4 | 5 | 顺子 |
| 5 | 5 | 三带二 |
| 6 | 6 | 三连对 |
| 7 | 6 | 钢板 |
| 8 | 4~5 | 炸弹 |
| 9 | 5 | 同花顺 |
| 10 | 6 | 炸弹（六张） |

**没有三带一**（4 张只有炸弹）。

### 2.3 `live/rules.py` 的 6 处错（465 手真牌验证）

| # | 问题 | 后果 |
|---|---|---|
| 1 | ~~"10" vs "T" 表示法不一致 → 直接崩~~ **此条不成立** | **更正**：那是控制台早期用**自造词表 `"S10"`** 量出来的，而老实现真实收到的词表是 `"ST"`（`_rank` 切出 `"T"`，正确）。用**生产词表**跑 1740 手，老实现**一次都没崩**。老代码内部确实存在 `10`/`T` 不一致，但真实输入永远触发不到 —— 是**潜在隐患**，不是已发生的缺陷 |
| 2 | **A 不能当小牌** | `A2345` 顺子判非法（数据里有 2 手） |
| 3 | **两个王不是对子** | 数据里有「三个2 + 两小王」= 三带二 |
| 4 | **二连对(4张)判合法** | 游戏里 4 张只有炸弹，会推出游戏不认的牌 |
| 5 | docstring 说「三带一(3+1)」合法 | 数据证明游戏里没有三带一 |
| 6 | 逢人配能力低估 | `2♥2♥2♠10♥`(打10) 是四个2的炸；`9♣10♣J♣Q♣+♥2` 是同花顺 |

**结论：`net/sim/meld.py` 是新写的唯一真源，不复制 `live/rules.py`。**
`live/rules.py` 改成「牌名 → 牌 ID」适配层，YOLO 面板照旧能跑。

### 2.4 训练素材

游戏日志 129 MB / 31 个文件：

- **63 个真发牌段**，其中 **55 局有完整结算**
  （`SendCardsService set roundID` 前缀共 126 行，另一半是不带 JSON 载荷的伴随行，须跳过）
- **55/55 局「出过的牌 + 结算剩的牌 = 108」分毫不差**
  → 这 55 局可**还原成明牌对局**（每家起手牌 = 出过的 ∪ 结算剩的；进贡/还贡那两张除外）
- `结算协议` 含 reward：`Rank`（**Rank[i] = 座位 i 的名次**）、`Upgrade`、
  `LeftCards`、`BombRatio` / `DoubleRatio` / `TotalRatio`
- `DonerChange` 与名次对不上的局是含进贡结算，**不是名次语义问题**
- ⬜ 8 局只有发牌没有结算，原因未查

### 2.5 ⚠️ 网络侧更正

**抓包 `capture.jsonl` 只存了每条帧的前 128 字节**（帧真实长度 46~4497），大帧全被截断。
能解出的牌局消息只有 3005 / 3006 / 3019 / 3003 / 3002 / 3004 / 3009 这 7 条。

**旧结论「级别：网络里确实没有」不成立** —— 发牌报文真实长度 310 字节，只看了前 128。
**那几条大消息的正文从来没被看过。**

另外：`parse` 解不出的 62 条完整帧是连接层报文（头里 `c0 0c 3b 51` 出现两次 +
base64 会话串），不是牌局；抓包里混了 3 个 host，只要 `hlxyxws.huanle.qq.com`。

## 3. 架构

```
net/sim/meld.py     牌型真源：legal_moves 枚举 + beats 比较
net/sim/rules.py    一局循环：发牌 / 进贡还贡 / 出牌(含接风) / 结算升级
net/sim/env.py      自对弈接口：状态与动作编码 + step / reward
train/selfplay.py   DMC 训练循环
net/advise.py       推理，接面板
```

### 分层与依赖

- `meld.py` 按**牌 ID** 工作（复用 `net/cards.py`），**不出现牌名字符串**
  —— `live/rules.py` 的 6 个 bug 有一半来自字符串处理
- `meld.py` **不依赖** `state.py` / `env.py`，是纯函数，可单独测
- `rules.py` 只依赖 `meld.py`
- `env.py` 只依赖 `rules.py` / `meld.py`
- `net/advise.py` 只依赖 `meld.py` + 权重文件（**推理时不加载模拟器**）

### ★ 不可动摇的纪律：不许明牌泄漏

模拟器内部是**明牌**（四家手牌都知道，否则判不了输赢），
但**喂给策略的状态只能含可观测信息**：我的手牌、已出牌、各家剩几张、
桌面、轮次、级别。**绝不能把对手手牌喂进去。**

泄漏的后果：会训出靠偷看才成立的打法 —— **训练分数漂亮、真机全废，而且静默失效**
（同「合成 val 骗过一次」的教训）。

座位一律**相对化**（自己 / 下家 / 对家 / 上家），四个座位共享一套策略。

## 4. 编码

### 4.1 状态（只含可观测信息）

| 内容 | 维度 |
|---|---|
| 我的手牌 | 108 |
| 已出过的牌（按座位分开） | 4 × 108 |
| 各家剩几张 | 4 |
| 桌面待压的牌 | 108 |
| 桌面牌型 + 主点数 | 10 + 15 |
| 谁要不起 | 4 |
| 轮到谁（相对座位） | 4 |
| 级别 | 15 |
| 最近 15 手的动作序列 | → LSTM |

「已出过的牌」+「各家剩几张」合起来就是记牌器给人类的信息 —— 网络不靠猜，线索与人类相同。

### 4.2 动作

每轮先用 `meld.legal_moves` 枚举合法着法，再对**这一批候选**逐个打分（非固定动作空间）。

每个候选编码为：`牌型 one-hot(10) ⊕ 主点数 one-hot(15) ⊕ 张数 one-hot(9，1~8 张 + 天王炸) ⊕ 是否含逢人配(1) ⊕ 牌 multi-hot(108)`

### 4.3 网络

```
最近 15 手出牌序列 → LSTM ─┐
                          ├→ 拼接 → 6 层 MLP → 每个候选一个 Q 值
状态 + 单个候选动作 ───────┘
```

形状对齐斗地主上的 DouZero（该配方在斗地主达到超人类水平）。**四个座位共享权重。**

## 5. 训练（DouZero 式 DMC）

### 5.1 学的是什么

```
Q(局面, 一手牌) = 出这手之后按当前策略打下去，本队最终能拿多少分
```

### 5.2 循环

```
1. ε-greedy 自对弈一局（四个座位共享策略）
2. 记录每个决策点 (局面, 出的牌)
3. 一局结束算 reward
4. 用「整局最终 reward」作为那些决策点的回归目标（不做 bootstrap）
5. 训练网络逼近
6. 重复（千万局量级）
```

牌类游戏中间步骤无即时反馈，只有终局有输赢 —— 直接回归终局结果，简单、稳、无偏差。

### 5.3 超参（初值，训练中可调）

| 项 | 初值 | 依据 |
|---|---|---|
| 动作历史长度 | 15 | 对齐 DouZero |
| ε（探索率） | 1.0 → 0.1 线性退火 | 前期必须充分探索，否则早熟 |
| replay buffer | 最近 50 万局 | DouZero 量级 |
| 优化器 / 学习率 | Adam / 1e-4 | DouZero |
| 网络 | LSTM(隐藏 128) + 6 层 MLP(512) | DouZero 形状 |
| batch | 32 局 | DouZero |
| 每 N 局存一次权重 + 跑一次基线评测 | 1 万局 | 用于看曲线 |

**这些不是拍脑袋的定值，是起点。** 吞吐测出来之后再定最终规模（见 §9 风险 1）。

### 5.4 reward

```
双上(1、2名) → +3     1、3名 → +2     1、4名 → +1      × 倍数
```

`Upgrade` 报的是**赢家**的升级数。**倍数必须带上** —— 打炸弹会抬倍数，
「赢了多打炸弹」有真实收益。**只写赢/输，这个策略就永远学不出来。**

**倍数是一个开关**：若最终想要「稳赢」而非「多赚」，把倍数项去掉重训即可。
**默认带倍数，看效果再定**（用户已同意）。

## 6. 验收 —— 第一层：裁判与模拟器

**这一层是地基，必须在训练开始前全绿。** 离线、秒级、每次动 `net/sim/` 必跑，做成一条命令。

因为**模型只会从裁判给的候选里挑**，所以只要裁判对，模型不可能推荐非法牌 ——
整个系统的正确性几乎全压在这一层。模型差只是「建议不够聪明」；
裁判错是「建议根本不能出」，而且在真机上才暴露。

### ① 真实着法必须能枚举出来（最重要）

55 局真实记录，每一手的局面喂给裁判，**用户当时真实出的那一手必须在 `legal_moves` 里**。
失败时报出「哪一局、第几手、真实出的是什么、枚举出的是什么」。

真实着法一定是合法的（游戏自己认过），所以不在里面 = 我们错了，无含糊空间。

**局限：55 局只能证伪，不能证明。** 抓得住「漏了牌型」这类大错，抓不住冷门组合未覆盖。
所以还需要 ②。

### ② 「谁压谁」逐条对齐

从真实对局反推的比较关系（炸弹 24 对证据来自 `net/events.jsonl` 的 465 手出牌；非炸弹对来自日志对局），`beats()` 必须**逐条一致**。

### ③ 不变量（抓低级错误）

| 不变量 | 违反了说明 |
|---|---|
| 一局打完 108 张牌总数不变 | 牌凭空多了或丢了 |
| 每局有限步内结束 | 死循环 |
| 轮到我领出时合法着法集合非空 | 枚举漏了（领出必须出牌，不能过） |
| 同一张牌不同时出现在两家 | 模拟器复制了牌 |
| **喂给策略的状态不含对手手牌** | **明牌泄漏，最危险** |

**最后一条必须自动化**：构造「对手手牌不同、其余相同」的两个局面，
若网络给两者的打分**一样** → 状态里确实无对手信息；不一样 → 泄漏。
**手动看代码看不出来，必须写成测试。**

### ④ 逢人配专项

- 1 张逢人配能凑哪些牌型、**不能**凑哪些（王不能当）
- 2 张逢人配的组合**完整且不重复**
- 牌库自洽：枚举出的着法塞回模拟器重判，必须自洽

### ⑤ 进贡 / 接风：从日志解，不猜

日志有 **2135 行进贡记录**。解出的规则拿数据逐条验（如「进贡必须给最大的牌」）。

### ⑥ 失败必须响

裁判遇到认不出的局面，**明着报错**，不静默返回「合法」或「过」。
宁可训练崩掉，也不要拿错规则偷偷训出一版废模型。

## 7. 验收 —— 第二层：训练

| 检查 | 判据 |
|---|---|
| 胜率 vs 随机 | 应很快到 90%+；**到不了说明状态/动作编码有问题** |
| **胜率 vs 贪心（有牌就出最小）** | **分水岭。打不过就是没学到** |
| 胜率 vs 人类着法（55 局） | 仅参考，**人类打得未必最好**，别当目标 |
| 同模型跑两次胜率 | 方差不能太大，否则评测不可信 |

**根本限制**：胜率是**我们自己模拟器里**的胜率。模拟器规则错了，曲线再漂亮也是假的。
这就是第一层存在的意义 —— **先把裁判和模拟器弄对，训练才有意义。**

## 8. 上线

### 8.1 推理链

```
GameState（网络实时状态）→ meld.legal_moves → 模型打分 → 建议
```

**推理不加载模拟器**，只需要裁判。上线的东西很轻：一个权重文件 + 裁判代码。

### 8.2 影子模式（用户确认要做）

第一版**不给建议，只记录**：

- 每个决策点把模型建议写进日志
- 同时记下**实际出了什么**、那一局最后赢没赢
- 攒几十局后回看：建议与实际选择的**分歧点**，以及那些分歧局最后谁赢

**为什么必须做**：模型在模拟器里的胜率只证明它在**我们的规则**下强。
影子模式是**唯一能在真实游戏上核对**的方式，且零风险（不动游戏、不出牌、只写日志）。

### 8.3 反馈回收（用户确认要做）

建议显示了但用户不采纳 → 回收这个信号，用于持续改进。

需要记录：决策点状态、模型建议、用户实际选择、该局结果。

**落盘**：`net/shadow.jsonl`，一行一个决策点，与 `net/events.jsonl` 同风格
（追加写、面板跟读、可用 `net/replay.py` 那套离线复盘）。

**注意**：用户不采纳**不等于**模型错（用户可能有模型不知道的信息，或反之），
采纳也不等于模型对。所以这份数据用于**分析**，**不直接当训练标签**。

**权重文件位置**：`runs/rl/<版本>/best.pt`，与现有 `runs/detect/guandanN/weights/best.pt`
的习惯保持一致。

### 8.4 红线

**绝不替用户出牌。** 不往游戏发任何报文。模型只输出给人看的建议。

## 13. 补充裁定（2026-09-25，Plan 2 开工前）

实施 Plan 2 前与用户确认的两条，**覆盖本文档 §3 / §5 里含糊的说法**。

### 13.1 一个 episode = **一手牌**，不是一局

§3 把 `rules.py` 写成「一局循环：发牌 / 进贡还贡 / 出牌(含接风) / 结算**升级**」。
新裁定：**「升级」不进 Plan 2**。

- episode = **发牌 → 进贡/还贡 → 出牌（含接风）→ 结算名次**，到名次出来即终止
- **级别（打几）由 env 当参数采样**，不从上一手的结果推
- **升级 / 过 A / 「下局谁先出」全部不实现** —— 一手一个 episode 时它们没有消费者

理由：§5.4 的 reward（双上 +3 / 1、3 名 +2 / 1、4 名 +1，× 倍数）本来就是**每手结算**
的量，不是局末的量。一手一个 episode 与它同构，也与 DouZero 一致：回合有界、训练快。

**代价（明说，别当成没这回事）**：训练分布与真人不同 —— 真人的级别是一局内爬上去的
（打 2 → 打 3 → …），不是均匀采样。若 Plan 3 评测显示级别分布有影响，再补局级循环。

### 13.2 Plan 2 的收尾边界 = env + 最小训练冒烟

Plan 2 交付四件：

1. `net/sim/rules.py` —— 一手牌的循环 + 结算名次
2. `net/sim/env.py` —— 状态/动作编码 + step + reward
3. **自对弈吞吐实测数字**（§9 风险 1 要求「先测吞吐再动训练」）
4. **最小训练冒烟** —— 随机初始化网络训几分钟，验 §7 第一行
   「胜率 vs 随机应很快到 90%+」。**这是唯一能在不搬出完整训练的情况下证明
   env 真能训的办法**；跑不到就是状态/动作编码有 bug，而不是「训得不够久」

**不碰** §7 的分水岭「打得过贪心」—— 那是 Plan 3。也**不碰** §8 的影子模式。

### 13.4 ⚠️ 实测推翻了 §5.4 的两句话（2026-09-25，54 局结算记录）

**(1)「倍数」不是打炸弹抬上去的。** 实测 54 局：

```
TotalBombRatio=1 的 49 局    ← 其中 36 局手上有 5~16 个炸弹/同花顺，倍数照旧是 1
FinalDoubleRatio ∈ {1, 1.5, 2, 2.5}   ← 这才是「倍数」，且是**发牌前选的加倍**，不是打出来的
TotalRatio = FinalDoubleRatio × RankRatio × TotalBombRatio
```

`FinalDoubleRatio` 是**发牌前**的选择，一手之内不变 ⇒ **它只是一个常数缩放，对最优策略零影响**。
（只有「一手之内变化的倍数」才会改变打法，实测没有。）

⇒ 本计划的 reward **不带倍数**，但留一个 `multiplier=1.0` 的钩子（一行开关），
Plan 3 想按 `FinalDoubleRatio` 分布采样随时能开。**这不是丢掉 spec 的要求，是那条要求的
前提在数据上不成立。**

**(2)「升级数 = 3/2/1」只对了两档。** 实测：

| 赢家名次形态 | 实测 RankRatio | 局数 |
|---|---|---|
| 1、4 名 | 1 | 18/18 ✓ |
| 1、3 名 | 2 | 12/12 ✓ |
| **双上（1、2 名）** | **3 或 4** | 13 / 11 |

双上那一格在 11/25 局里是 **4**。同一 `Rank`、同一战前 `trump`、同一 `TrumpOwner`
既能出 3 也能出 4 ⇒ 还依赖本计划没抓的字段（**属于升级/过A 的范畴**，按 §13.1 不在 Plan 2 内）。
⇒ reward 用 3，**在验收里把这一类单独报出 3/4 分布**，不当成验收失败。

### 13.5 「一手牌什么时候结束」已有硬证据（55 局）

```
双上（1、2 名）   -> 只出完 2 家就终局    25/25 局
1、3 名 / 1、4 名 -> 出完 3 家才终局      30/30 局
```

⇒ 局终条件是 **「同一队包了前两名」立即终局，否则等 3 家出完**，
不是「3 家出完」一条（那样 25 局双上会被多打几手）。

双上局的败方 3/4 名：**23/25 局按剩牌少者排第 3**，2 局相反。
⇒ 模拟器按「剩牌少者排前，同数按座位小者排前」实现；**这 2 局的偏差对 reward 无影响**
（双上时败方名次谁 3 谁 4 不改变形态），验收里只报数不作失败。

### 13.6 还贡 ≤ 10：25/25 条硬证据

`NotifyReturnTribute` / `TributeSectionEndService` 共 25 条还贡记录，
`card=` 全部解码后点数 **≤ 10**（跨四个花色、两副牌）。
⇒ 「还贡必须给 ≤10 的牌」直接可用，不用再猜。

**还贡给哪一张**是受贡方的选择（25 条里不唯一），模拟器按「≤10 里最小的那张」定死并记明。
**进贡给最大的牌**只有 5 条直接记录且我的对齐脚本不可靠，**按规则实现 + 验收里逐条报差分**。

### 13.7 ★ 出牌轮转的三条实测规则（2026-09-25，55 局逐手回放定下来）

写模拟器之前**必须先知道这三条**，因为它们全都与直觉相反，而且错了不会报错、
只会让规则引擎在真对局上大面积判「压不过桌面」。这三条都是拿 55 局真实对局
**逐手回放**（spec §6① 在牌局层的对应物）逼出来的，不是推的：

| # | 规则 | 按直觉写会怎样 |
|---|---|---|
| ① | **「下家」是 `(s - 1) % 4`** —— 出牌顺序是 `0 → 3 → 2 → 1 → 0`。报文的座位号**不是**按顺时针递增给的 | 按 `(s+1)%4` 写：**55 局一局都走不通**（第 2~3 手就崩） |
| ② | **每出一手，`passed` 清空** —— 一手牌打出来等于**重新开一轮**，其余三家重新获得机会（含之前已经「要不起」过的） | 不清空：55 局只有 4 局能走通；38 局在中途被判成「压不过桌面」 |
| ③ | **清桌后如果桌面主人已经出完，领出权给他的队友（接风）**；队友也出完了就顺着 `(s-1)%4` 找下一个还有牌的 | 判据写成「所有人过完」也**等价**（见下），但漏了「主人出完」这一支就会把接风那手判成压不过 |

**为什么 `tools/decision_points.py` 一直没暴露 ①**：它只需要「谁出完了」这一个判据
（用 `(table_seat + 2) % 4` 找队友，**方向无关**），从来没算过「谁该接着出」。
Plan 1 的验收①也只验「这一手是不是合法牌型」，不验轮转。**这是 Plan 2 才第一次
碰到的东西。**

**关于 ③ 的一个细节**：接风看起来有「立即给队友」和「三家过完再给队友」两种写法。
实测两种**结果等价** —— 因为主人出完后，队友轮到时若压不过就先过，三家过完清桌，
再由队友领出，落点相同。写「三家过完再给队友」（即只在 `_lead_after` 里处理）
更简单，且 55/55 全过。

**验收方式（Plan 2 的 Task 5）**：`tools/accept_sim.py` 拿 55 局真实对局逐手回放 ——
每一手都要求「我们算出的轮转与日志一致」且「真实着法在候选里」。**这是牌局层的地基。**

### 13.8 进贡规则实测（2026-09-25，25 条记录，落实 §6⑤）

§13.6 说「进贡给最大的牌」是基线。现在有数了，结论是**维持基线，不加豁免**：

| 候选规则 | 命中 |
|---|---|
| **贡全手最大的牌**（本实现） | **18 / 25** |
| 除大王外最大的牌 | 13 / 25 |
| 除大王与级牌（逢人配）外最大的牌 | 5 / 25 |

**而且有 8 条确实贡了王**（王是最大牌时照贡）—— 所以「王不贡」这条豁免与数据直接冲突。

7 条不符的模式是「手上持王或级牌时贡了别的」（6 条持王、1 条持级牌），
但 7 条太少、且与那 8 条互相矛盾，**不足以改实现**。
`tools/accept_tribute.py` 会把这个比对连同三条候选规则的得分一起打出来，
样本攒够了自然能看出模式。

**「还贡 ≤ 10」是硬证据，25/25 全过**（§13.6），这一条判失败；
**「贡最大的牌」是基线，只报告不判失败**。

**这一条的账要记清**：进贡在训练里默认**关**（`EnvConfig.tribute=False`，§13.1），
所以这条基线的不确定性**不阻塞 Plan 3**。要开进贡训练之前，先把这一项跑出稳定模式。

## 14. Plan 3（训练）开工阶段的两条更正与三条实测（2026-09-25）

### 14.1 ⚠️ §5.3 的 replay buffer「最近 50 万局」**按字面做不到**

那句话只说了「多少局」，没说**存什么**。按存编码好的张量算：

```
每个决策点 state(700) + action(143) + history(15×147) = 3048 个 float32 ≈ 11.9 KB
每局约 131.6 个决策点 -> 每局 1.53 MB
    10,000 局 ->  14.9 GB      100,000 局 -> 149 GB      500,000 局 -> **747 GB**
```

**改成存「这一局是怎么打出来的」**（发牌 108 个牌 ID + 每步选中的候选下标），
采样时重放一遍：

```
每局约 1.9 KB      10,000 局 -> 18 MB      100,000 局 -> 185 MB      500,000 局 -> 923 MB
```

代价是 CPU（重放一局约 27 ms），而网络很小 —— 拿 CPU 换内存划算，
§5.3 那个数字因此**从做不到变成做得到**。实现见 `train/replay.py`。

### 14.2 ⚠️ §5.3 的「batch 32 局」不能从斗地主直接搬过来

DouZero 的 batch 是 32 **局**，而斗地主一局约 20 个决策点 -> 约 640 个位置。
掼蛋一局实测 **131.6 个决策点**，同样 32 局就是 **约 4,200 个位置，是它的 6.5 倍**。
「32 局」这个数在两种游戏里不是同一个东西。要按位置数来定 batch，或者接受慢 6.5 倍。

### 14.3 实测：训练步的瓶颈是**网络前向**，不是规则引擎

规则引擎已经优化到 95 局/秒（见提交 `perf: 自对弈吞吐 29~37 → 95 局/秒`），
但接上训练循环之后只有 14.2 局/秒。剖面把差额指出来了：

```
q_values  被调用 37,689 次，累计 70.8 秒   <- 一次前向只算一个局面（候选 <10 个）
torch.lstm 11.0 秒（43,169 次）· torch.linear 19.8 秒（302,183 次）
```

一次前向只算**一个**决策点的候选，GPU 的批处理完全浪费。
改成「32 局同步推进、各走一步、攒成一批再前向」之后，同样次数的前向变成 1/32
（`train/selfplay.py` 的 `generate_batch` + `train/net.py` 的 `q_argmax_batch`）。

**下一处同类的浪费是评测器**（`train/eval.py` 也是一步一次前向）。
当前它只占 1 小时训练约 6% 开销，所以先放着；**要跑长训练（几天）之前该把它也批量化**。

### 14.4 实测：评测噪声与判据阈值的依据

同一个网络换 6 个种子各测 200 局 -> **4.8% ± 1.4%**（二项理论值 ≈1.5%）。
所以 200 局的噪声约 ±2%，判据「明确打得过贪心（≥55%）」不会被噪声骗过。
**100 局时噪声约 ±5%，不够用** —— 早期用 100 局测出过「29% vs 15%」，
看着像 bug，其实只是样本太小。

### 14.5 贪心基线的强度（判据有没有意义，取决于这个）

```
随机 vs 随机 = 50.0%      <- 评测无偏、赛制对称
贪心 vs 随机 = 83.2%      <- 基线明显强于随机 =>「打得过贪心」是个有意义的门槛
贪心 vs 贪心 = 49.3%      <- 对称性自检
```

基线定义（2026-09-25 与用户确认）：**能出就出、要出就出最小的那一手**
（排序键 `(张数, 主点数, 牌型)`），能压就压、从不主动过。
`train/policies.py` 的 `greedy_policy`，行为与强度都有测试钉着
（`tests/test_train_policies.py`）。
