## 四、出牌推荐：训练思路

**一句话**：把出牌推荐做成一个**值函数回归**问题 —— **不学「这手牌好不好」的中间判断，
直接回归「出了这手之后，这一手牌我们队最后拿了多少分」**；数据全靠**自对弈**产生。
（就是 DouZero 那套 DMC —— 设计文档第 5 节的标题原文就是「训练（DouZero 式 DMC）」。）

### 1. 形式化：到底在学什么

```
Q(局面, 一手牌) = 出这手之后，按当前策略打下去，本队最终能拿多少分
```

- 标签是**整手牌的终局结果**，不是下一步。牌类游戏中间步没有即时反馈，
  直接回归终局最省事也最稳 —— **不做 bootstrap**，不是 TD / Q-learning。
  这就是 DMC 里「Monte-Carlo」那一半。
- 「Deep」那一半：Q 是神经网络（`train/net.py::QNet`），且**以动作为条件** ——
  `QNet.forward(state, action, hist) → 一个标量`。
- **评估动作**：决策时对**每一个候选**打分再取最大
  （`train/net.py::q_values` → `net/advise.py::advise`）。
  **训练与上线走的是同一个 `q_values`**，不是两份码。

### 2. 动作评估真的在起作用（2026-09-27 实测）

同一个局面下，候选之间**唯一变化的输入就是动作编码** ——
所以 Q 在候选之间的**离散度**，直接就是「动作通道用了多少」。

| | 1407（144 万局） | 随机初始化的同结构网络 |
|---|---|---|
| 决策点 | 1644 | 2355 |
| **候选间离散度（max−min）中位** | **0.401** | **0.000**（p90 0.001） |
| **首选与次选之差 中位** | **0.123** | 0.000 |
| 首选次选打平（< 0.01） | 5.7% | 100% |

**两个限定得说清**：① 训练时只见到「实际出的那一手」，
**没出的牌靠泛化外推**；② 边际很薄 —— 首选次选之差中位 0.123，
而标签尺度是 **±1~3**。

### 3. 奖励

零和、**从「出牌人」视角**（四个座位共用一套权重，所以必须零和、状态必须相对化）：
`±points`，`points` 只看赢家队的**最差名次** —— 双上 3 / 1、3 名 2 / 1、4 名 1。

⚠️ **不带倍数。** 设计文档原本要 ×倍数（理由「打炸弹抬倍数」），
但 2026-09-25 实测 54 局把那个前提推翻了：真正的倍数是 `FinalDoubleRatio`，
**发牌前就选好、一手之内不变** —— 那只是常数缩放，**对最优策略零影响**。
代码里留了 `MULTIPLIER = 1.0` 一行开关。

### 4. 一个 episode = 一手牌

发牌 → 进贡/还贡 → 出牌（含接风）→ **出名次就终止**。
升级 / 过 A / 「下局谁先出」**全都不实现**（一手一个 episode 时它们没有消费者），
级别当参数采样。代价是**明说**的：真人是一局内级别往上爬，训练是均匀采样。

### 5. 三个编码

| | 维度 | 内容 |
|---|---|---|
| 状态 | **700** | 我的手牌 108 + 四家出过的牌 432 + 各家剩几张 4 + 桌面 108 + 桌面牌型 10 + 主点数 15 + 谁要不起 4 + 轮到谁 4 + 级别 15 |
| 动作 | **143** | 候选由规则引擎枚举（含「过」那条） |
| 历史 | **15×147** | 最近 15 步右对齐；147 = 动作 143 + 出牌人相对位置 4 |

**唯一的硬纪律：不许明牌泄漏。** 做法不是靠注释，是靠**类型** ——
`Observation` 里**根本没有**「四家手牌」这个字段，`encode_state` 只吃 `Observation`，
**结构上就泄不了**；`tests/test_env_leak.py` 再钉一遍。
座位**一律相对化**（0 = 自己 / 1 = 先于我 / 2 = 对家 / 3 = 下家）。

### 6. 训练循环：四步一循环

1. **ε-greedy 自对弈打一批** —— 32 局**同步推进**（各走一步、攒成一批再前向）。
   剖面显示不这么做的话一次前向只算不到 10 个候选，批处理全浪费
   （`q_values` 被调 37,689 次、累计 70.8 秒）；同步推进把前向次数降到 1/32。
2. **进 replay buffer** —— 存**紧凑记录**（级别 + 发牌 + 每步选中的候选下标），
   约 1.9KB/局；采样时**重放**回决策点（约 27ms/局）。**拿 CPU 换内存**：
   「存最近 50 万局」按存张量算是 747GB，按紧凑记录是 923MB。
3. **从 buffer 有放回采 32 局** → 重放 → 拼张量 → 一步 MSE + Adam(lr=1e-4)。
4. **每 1 万局**评测一次（vs 随机 / vs 贪心各 200 局），**超过历史最好就存 `best.pt`**。

ε 按**局数**退火（1.0 → 0.1，25 万局），**不按时间**。这是踩出来的：
按时间退的话，9 小时预算下跑到第 25 分钟 ε 还有 0.96 ——
「加时长收益越来越小」的真因是**探索没退下去**，不是撞墙。

### 7. 对手怎么配（现状）

`opp_mix=0.5`：一半的局把**一个队**换成固定对手，学习那一队照旧打网络。

**固定对手是谁，由 `--pfsp` 决定**（2026-09-27 加，默认关 = 老行为）：

| | 对手 |
|---|---|
| **不带 `--pfsp`** | 80% 贪心 / 20% 随机（老行为） |
| **带 `--pfsp`** | 混合局里 20% 给贪心，其余按 **PFSP** 抽**模型自己的历史版本池**（每 2 万局存一个快照，留最近 20 个）。权重 ∝ `p(1−p)`（专挑五五开）+ 20% 均匀下限。实现见 `train/pool.py` |

两条相关的纪律：

- **只有学习那一队的决策点该进训练目标** —— 这个约定曾经有 bug（`expand` 把固定对手的
  着法也产出了），**2026-09-27 已修**，见 §七.2。
- **`--learn-all-seats` 是 A/B 的对照臂**：恢复「四家都学」的老行为。

**池子做完了但没验出好处**（2026-09-27）：见 §七.1 与
`docs/superpowers/plans/2026-09-27-opponent-pool-delivery.md`。

### 8. 多进程

`--workers N`：worker 进程只打牌（纯推理、CPU），主进程学习。
跨进程只传**紧凑记录**（传张量 IPC 会爆）；每 1000 局把 `state_dict` + ε 广播回 worker。
**ε 必须由主进程按全局局数算再广播** —— 各 worker 自己算会各自以为自己是全部。

### 9. 判据与三个薄弱点

- **判据（就是退出码）**：`vs 贪心 ≥ 55%`（50% 只是五五开，不算打过）
- **收尾打印**：vs 随机 / vs 贪心（两个种子看方差）/ **炸弹浪费率**（只报告，不判据）
- **影子模式**：真机上每个决策点记下「模型建议了什么 / 我实际出了什么 / 这手最后赢没赢」
  → `net/shadow.jsonl`

**三个薄弱点（2026-09-27 诊断）**：

1. **标签的信噪比太低。** 现在 95% 的局都赢 ⇒ 标签里 95% 是「+3」，
   「炸 vs 不炸」的区别全挤在那 5% 里。**不是没被惩罚，是惩罚淹在噪声里。**
   首选次选之差中位只有 0.123 也印证了这点（边际本来就很薄）。
2. **尺子饱和了。** 判据是 `vs 贪心 ≥ 55%`，现在 95.2% —— 早没有区分度；
   而且贪心**惩罚不了浪费**（它从不主动炸、也压不住你）。
   `opp_mix=0.5` 的实际含义是：**一半算力花在一个已经打穿的对手身上**。
3. **没有 league。** 对手只有「当前的自己」和贪心，没有历史版本对抗 ——
   也就没有「你浪费一手会真的输」的压力。

**第 3 条的整改已经做完了**（league + PFSP，`train/pool.py`），**但那一轮实验作废**：
池子在混合局里只拿到 **20%** 的份额（设计是 80%，代码用错了另一个 `greedy_share`），
**整轮只给了设计剂量的 1/4**；而且实验被内存打死在 2.1 万局。
所以「池子有没有用」**这一轮没有回答**。
详见 `docs/superpowers/plans/2026-09-27-opponent-pool-delivery.md`（结论改过一次，评审抓的）。

**同一轮实验里撞出两件比池子更该先处理的事**：

- ✅ **`--init` 与 ε=1.0 的坏组合 —— 2026-09-27 已修**：热启动时 ε 起点自动压到 0.3。
  修之前 ε 仍从 1.0 起，头一万多局近乎随机，把热启动冲掉 ——
  三臂**全都**比起点差（95.2% → 90~94.5%）就是这件事。
  （修之前实测：同一命令 25 秒后 vs 贪心 92.5%/87.5%；修之后 95.0%/92.0%。）
- ⚠️ **固定 200 局评测有系统性偏差**：同一份权重，200 局报 96.5%、400 局报 92.8%
  （即第 201~400 局只有 89.1%）。判据（退出码）仍有效（与历史跑可比），
  但 `>> 评测 @` 那些行**不能当泛化能力读**。

**所以下一步的顺序变了**：先修 `--init` 的 ε，再重跑实验（内存上要两臂或串行），
池子仍是待判的那个；若仍无效果，再按原计划转「**换目标（信用分配）**」而不是加算力。

## 五、怎么跑

### 打牌时（面板 + 影子模式）

```powershell
.venv/Scripts/python.exe -m net.launcher
```

| 参数 | 用途 |
|---|---|
| `--dry-run` | 只检查环境，不动系统代理 |
| `--no-panel` | 只起抓包，不开面板（调链路用） |
| `--no-advice` | 关掉影子模式（不加载权重） |
| `--no-show-advice` | 算建议但不显示（记录里如实写 `advice_shown:false`） |
| `--level N` | 手输级别（日志读不到时） |
| `--console` | 用终端版面板 |
| `--yes` | 跳过确认 |

### 训练

```powershell
$env:GUANDAN_DEVICE="cpu"      # 实测 CPU 反而快：这个循环以 Python 为主，GPU 只抢显存
.venv/Scripts/python.exe -m train.selfplay 32400 --opp-mix 0.5 --workers 2
```

- **判据（退出码）**：`vs 贪心 ≥ 55%`（spec §7 的分水岭：50% 只是五五开）
- 收尾会打印：`vs 随机`、`vs 贪心`（**两个种子，看方差**）、**炸弹浪费率**、曲线
- `--eps-games`：ε 退火到 0.1 所需的**局数**（默认 25 万）。
  ⚠️ **跑短实验一定要把它调小**，否则前大半段都在近乎随机地探索，两组实验测不出差别
- `--buffer`：默认 5 万局（约 92MB）；spec 原数是 50 万局（923MB）
- `--pfsp`：开**对手池**（默认关 = 老行为）。开了之后每 `--snap-every` 局存一个快照进池，
  池子留最近 `--pool-size` 个。⚠️ **内存**：每个成员 7.8MB × 池子大小 × worker 数 ——
  **别把多条开池子的臂并发跑**（2026-09-27 三条并发把机器打爆过）
- `--init <ckpt>`：热启动。**ε 起点会自动压到 `EPS_START_WARM = 0.3`**
  （`--eps-start F` 可显式覆盖），并打进日志头 —— 2026-09-27 修。
  修之前 ε 仍从 1.0 起，头一万多局近乎随机、**把热启动整个冲掉**
  （三臂实验就是这么被盖住的，见 §四.9）
- `--learn-all-seats`：**对照臂专用**，恢复「固定对手的着法也进训练目标」的老行为
- `--out-dir <dir>`：两臂必须落在不同目录，否则后跑的覆盖 `best.pt`
  （面板按修改时间挑权重，会**静默换源**）
- ⚠️ **`--workers` 的推荐值尚未钉准**，见 §七.4

## 六、实测数字（口径写在这里，引用时别丢）

### 三版权重，同一把尺子

| 存档 | 训练量 | vs 贪心（400 局，同种子） | 炸弹浪费率（面对贪心，60 局） |
|---|---|---|---|
| `runs/rl/20260926-0033/best.pt` | 20 万局 · **纯自对弈** | 87.8% | 5.1% |
| `runs/rl/20260926-0940/best.pt` | 18 万局 · 混对手 | 87.2% | 5.1% |
| **`runs/rl/20260926-1407/best.pt`** | **144 万局 · 混对手** | **95.2%** | **4.2%** |

- 1407 直接对打 0033：**62.3%**（400 局）
- 1407 **到结束前 16 分钟还在刷新 best** → **没到顶，继续练有收益**
- 吞吐 **44.5 局/秒**（1,441,760 局 / 9 小时 1 分）

### 评测是**确定性的**

`match` 的牌由固定种子抽出（每次评测都是**同一批牌**），策略全是确定性的
（网络 argmax、贪心取最小、随机用固定 rng）。实测：同一个网络连跑两次，
结果**一字不差**（90.0% / 90.0%，与存档自报一致）。

→ 所以日志里 `vs 贪心` 的涨跌是**真实的行为变化，不是采样噪声**。
→ 但反过来说：**它只是同一批 200 局上的表现**，不能当泛化能力的唯一依据。
（`selfplay.py` 里那句「200 局的噪声约 ±2%」说的是**换种子**时的不确定度，不是重复评测。）

### 炸弹浪费率有**两个**数

`train/eval.py::bomb_waste` 的 docstring 明写：**自对弈**和**面对贪心**是两个数，
**玩家看到的是后者**。两个都要看，别只量一个。

| 存档 | 自对弈 | 面对贪心 |
|---|---|---|
| 0033 | 5.2% | 5.1% |
| 0940 | 4.2% | 5.1% |
| 1407 | 6.4% | 4.2% |

### 真实对局（`net/shadow.jsonl`）

- 7 次开会话，权重依次 0033 → 0940 → 1407。**文件是追加累积的 —— 读的时候必须按 `session` 行切分**，否则会把老版本的问题算到新版本头上
- 12 局 / 223 个决策点；与建议第一选一致的比例 **62.6%**
- 最后一次会话（1407）：40 个决策点，**跟建议 90%**（之前几次是 40~66%）—— 明显更信它了
- 「桌面有牌」的决策点里**模型首选是炸弹**的比例：
  0033 会话 **56/140（40%）** → 1407 会话 **3/34（9%）**；
  其中「本来能用普通牌压」（= 真浪费）的：**22/140 → 1/34**

## 七、已知问题 / 没做完

### 1. 炸弹浪费**没治好**（用户最初的抱怨）

面对贪心 5.1% → 4.2%，**只有约 1.6 个标准差 —— 不足以称为改善**。
真实对局里症状明显轻了（40% → 9%），但残差还在。

**根因（2026-09-27 诊断）**：`opp_mix=0.5 / greedy_share=0.8` 意味着
**一半的训练局在跟一个已经被打穿的对手下棋**（95% 胜率）。
贪心现在教不了任何东西；更要命的是它**惩罚不了浪费** ——
它从不主动炸、也压不住你，你白炸一手它抓不住。
所以炸弹浪费在训练分布里**至今没有代价**。

方向：把固定对手从贪心换成**模型自己的历史版本**（league），而不是继续加算力。

**2026-09-27 的整改进展**：league 已经做出来并接进训练（`train/pool.py` + `--pfsp`），
**但没验出好处** —— 三臂 A/B/C 里池子臂的炸弹浪费不比只修 `expand` 的那一臂低
（同 2 万局：对池中位 5.4% vs 4.2%，方向是反的），而且没有任何一臂在 `vs 贪心` 上
超过起点（95.2% → 90~94.5%）。实验被内存打死在 2.1 万局，所以准确说法是
「**没测出来**」。台账见 `docs/superpowers/plans/2026-09-27-opponent-pool-delivery.md`。

### 2. `replay.expand` 会把固定对手的着法当训练目标（真 bug）—— ✅ 已修

**2026-09-27 已修**（提交 `193c7c3`）：`GameRecord.learn` 带上学习座位，
`expand` 按它过滤（**局面每一步照走，只过滤产出**）。对照臂用 `--learn-all-seats`。

**当时的诊断**（留着是因为「它是怎么被找到的」值得记）：设计明写
「固定对手的着法**不进训练目标**（记进去等于拿它当老师）」，`generate_batch` 的
现场抓取（`caps`）也确实只记学习那一队 —— **但单进程那条路几乎不用现场抓取**：

```python
pts, y = fresh.get(id(rec)) or replay.expand(rec)
# buf.sample 从 5 万局里有放回抽 32 局，撞上刚打那 32 局的期望是 0.02 局/步
```

而当时的 `GameRecord` 只有 `level/first/hands/actions`，**没有「哪一队是学习的」**，
`expand` 只能把四家全产出成训练点。实测 `opp_mix=0.5`：
6008 个重放训练点里 **1040 个（17.3%）是固定对手（贪心）的着法**，
标签却是那一局的胜负。`train_parallel` 更彻底 —— 它**永远**走 `expand`。

⚠️ 但要如实说：**1407 带着这个 bug 练到了 95.2%**，它不是拦路虎。
（修完之后的三臂实验里，只修它的那一臂在 2 万局时确实比老行为好：
92.8% vs 90.2%，+2.6 个百分点 —— 但那是**同一批 200/400 局**上的差，
且实验被内存打断了，不足以当结论。）

### 3. 验收的「换源」有缺口（那条红测试的真因）

`tests/test_tribute_records.py` 红，是因为**日志轮转**（最早的实时日志只剩 09-24，
进贡记录被转掉了）。而 `load_tributes()` **没有快照兜底**：
`load_corpus()` 有（`data/game_corpus.json` 在，报告里也会写「来源是快照还是实时日志」），
`load_tributes()` 直接读实时日志目录 —— 于是进贡那一环
**读不到证据，却没说数据是从哪来的**。这正是本项目「**换源必须可见**」纪律的缺口。

### 4. 多进程的收尾没做完

- 10 分钟短跑 + HANDOFF 更新 + learner 走 GPU 的那次测量（计划里的 Task 4）
- **吞吐曲线要重测**：`tools/bench_train.py` 每档只跑 45 秒，
  把 `spawn` + `import torch` 的启动成本全摊进去了 ——
  它报 workers=2 是 33.8 局/秒，而实际 9 小时跑出 **44.5**。
  **短跑测出来的吞吐不能拿来选并行度。**

### 5. 两份 replay 实现曾经并存

`net/panel.py --replay` 与 `net/replay.py` 是两套独立的「把抓包当实时流回放」，
同一个 `DEFAULT_CAPTURE`、同一件事。`net/replay.py` 已删，
但**这说明「副本会漂」在这条线上真实发生过一次**，值得记进纪律。

### 6. `net/rawdump.py` 是**隐式依赖**

它没有被任何代码 import（mitmproxy 用 `-s` 按路径加载），
所以**任何「谁引用谁」的自动检查都看不出它还在用**。删代码时这类东西最容易误伤。

## 八、本轮复盘：六个判断失误

1. **用 45 秒短跑测吞吐** → 把进程启动成本摊进去了，低估稳态（报 33.8，实际 44.5）。
   **短跑不能拿来选并行度。**
2. **建议在 22.7 万局停掉 0940**，依据是「vs 贪心」在固定 200 局上的下降趋势。
   1407 证明继续练有大收益 —— **固定小样本上的趋势不是可靠路标。**
3. **把 `replay.expand` 污染当成 0940 退化的主因** → 过度归因。
   1407 带着它练到了 95.2%。
4. **`bomb_waste` 的 docstring 是我自己写的**，里面明写「两个数都要看、
   玩家看到的是面对贪心那个」—— 我量的时候还是只量了自对弈那个，
   得出了「没改善」的错误中间结论。
5. **读 `shadow.jsonl` 时没先按会话切分** —— 那是追加累积的文件。
   混着读会把 0033 的问题算到 1407 头上（第一次数出「53 个首选炸弹」，
   实际 1407 会话只有 3 个）。
6. **划死代码时，把「留下的东西的依赖」划进了删除档**
   （`match_played.py` / `table_gt.py` 被保留的 `eval_table.py` import；
   `tools/snapshot_logs.py` 被 `game_log.py` + 一个测试引用）。
   **靠逐文件引用核查才拦住。**
